# v0.2 source-comment and Ddoc review

**Status:** In progress; partial source inventory, not a completed release gate.  
**Branch baseline:** `release/0.2` at `1465ee41ebc23d7f5538d5e2d0a8b313a64f7411`  
**Frozen public API:** `freeze/api-0.2.0` at `1ea67cb6ffb2c887f78d160249a293ad74ba5cda`

## Scope and standard

The release documentation standard is `docs/ddoc-style.md`.
The source Ddoc attached to declarations is authoritative; generated DDox is a
derived publication artifact. Review must distinguish the supported root
import (`import raster;`) from package-private constructors and execution code.

A complete review requires reading **every** supported public declaration and
nontrivial internal function, checking the actual rendered public-only DDox site,
and recording human judgments on semantics and explanations. CI success alone
does not establish that standard.

## Identified and corrected

- `writable_view.d` described its public view as available “from E5.4g.1
  onward.” This was development-history vocabulary rather than useful consumer
  documentation. The module now states the current public/API versus
  package-internal boundary without changing code or declarations.

## Third pass: remaining root-exported API modules

The sixteen remaining root-exported modules were fetched and screened for
module-level Ddoc, release-phase references, and the broad subject of their
public contract:

- Sample/layout: `sample.d`, `byte_layout.d`.
- Pointwise and arithmetic: `fill.d`, `transform.d`,
  `transform_into.d`, `zip_transform_into.d`, `arithmetic_into.d`,
  `transform_allocated.d`.
- Reduction: `reduction.d`.
- Neighbourhood policy/execution: `neighbourhood_shape.d`,
  `border_policy.d`, `neighbourhood_into.d`.
- Copy/conversion: `copy.d`, `conversion_policy.d`,
  `conversion.d`, `conversion_allocated.d`.

Three source comments still named internal milestone identifiers even though
the documented behavior is part of the current API. These were revised:

- `transform.d`: describe semantic pointwise transformation without
  referring to M2.2.
- `reduction.d`: state the documented NaN extrema outcome without
  referring to M3.1.
- `conversion_allocated.d`: state that exact conversion is the sole
  supported v0.2 policy without referring to M3.5.

This completes an **initial module-level scan** of the root-exported modules;
it does not complete function-level Ddoc, trusted-proof, or generated-site
review. In particular, public `border_policy.d` types must not be
misrepresented as currently implemented runtime border synthesis.

## Outstanding release qualification

- Review the rest of the public root-exported modules and all their callables.
- Audit nontrivial private/package functions and document why their unusual
  algorithms, ownership rules, and numerical branches exist.
- Check every `@trusted` boundary against its safety argument; a doc review
  cannot substitute for executable negative/positive safety tests.
- Generate the **public-only** DDox artifact and inspect actual navigation,
  symbol visibility, and all required rendered Examples.
- Reconcile tutorial, how-to, glossary, and accuracy documents against the
  frozen source contract.
- Run the release documentation and API gates for the final changes and record
  their outcomes in issue #198.

Do **not** mark the Source Comments/Ddoc or public-only DDox checklist
items complete until those checks have been performed and verified.
